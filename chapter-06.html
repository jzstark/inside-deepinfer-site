CHAPTER 06

Keep the host and device busy

Chapter 1 found two oddities in DeepInfer’s loop. One call to the worker can handle work from two steps, and the outer loop must flush a pending step after the scheduler reports no unfinished requests. Chapter 5 found a third: a result can arrive for a request that the scheduler has already reset. All three come from one design choice. The host plans the next step before it has read the result of the current one.

The question

The host must choose step N + 1 before it has read step N’s result. What can it decide without that result? What must the device supply instead? When may storage or metadata from step N be reused?

6.1 Overlap has a limit

Two parties take part. The host is the CPU process that schedules requests, prepares metadata and submits work. The device executes submitted work in order on a queue, called a stream. Submitting work and executing it are different events. The host can queue a forward pass and move on before the device starts it. Chapter 4 introduced events: markers in the queue that the host can wait for.

A decode step has two device operations here: a forward pass that evaluates the model, and sampling that chooses tokens from its output. The host has four kinds of work: scheduling, submission, post-processing of sampled tokens, and engine callbacks. The next forward needs the tokens chosen by the previous sample. The question is whether the host must read them first.

BASH
python3 labs/13_overlap.py

The experiment assigns durations to these operations and simulates both orders. In the synchronous order, each call submits forward and sampling, waits for sampling to finish, then post-processes its own result. The ZOS order follows Worker.execute_model_step (worker.py, lines 113–189). During decode call N + 1, the host:

  1. prepares inputs and queues forward N + 1;
  2. waits for sample_end_evt of step N, then post-processes step N;
  3. queues sampling for step N + 1 and runs the engine callbacks in pre_sampler_sync;
  4. records sample_end_evt for step N + 1 and keeps the step’s state for the next call.

The lab puts forward and sampling on one device queue, so forward N + 1 cannot start before sample N finishes even though the host queued it earlier. The worker’s comment at line 231 states that ordering for the correction work queued before forward; this chapter’s release table returns to the cases where a single queue is assumed rather than shown [7].

In the baseline, the device does 12 units of work per step: forward 10 and sampling 2. The synchronous run takes 20. Its device is idle for 8 units while the host post-processes (4), schedules the next step (3) and submits the next forward (1). The host also waits 10 units for each sample. The ZOS run takes 12, the device’s own work, and the host waits only 2. Its ten units of host work fit behind the next forward. Figure 6.1 draws the first three steps of both runs.

The other two cases show the limit. When scheduling takes 12 units, the host needs 19 units per step, more than the device’s 12. ZOS still helps, from 29 to 19 units, but the device now idles for 7 units every step. Overlap can hide host work only behind device work that is already queued. In the third case, post-processing takes 14 units. The host cannot queue sample N + 1 until it has post-processed step N, so the device finishes forward N + 1 and then waits. The gap is 14 + 1 − 10 = 5 units: post-processing plus the sampling submission, less the forward. Overlap moved the waiting; it did not remove the dependency.

The first sample ends at time 16 in both baseline runs. Overlap does not shorten the first step, because nothing is queued before it. At the end, the ZOS run must still wait for and post-process its pending step, the flush from chapter 1. The step interval describes repeating throughput; the fill and the drain are separate costs.

One more detail is visible in the code order. The worker records sample_end_evt after the callbacks, not immediately after queuing sampling (lines 161–168). The lab models that event as complete at the later of the sampling end and its own submission. Waiting for the event can therefore take longer than waiting for sampling itself would.

6.2 One request crosses two steps

Chapter 1 identified the asynchronous-scheduling precedents acknowledged by the deployment Q&A. The idea carried forward is to overlap host preparation with device execution. The question here is how DeepInfer makes that overlap work when the host’s information is a step behind. Its implementation matches rows by request identity, supplies tokens and length corrections on the device, and retains results and metadata until their readers are finished. The next sections trace those obligations. They explain this implementation’s choices without claiming that row remapping or deferred release originated here.

Overlap has a price in information. When the host schedules step N + 1, step N is still running. The host does not yet know which token step N will sample. If step N verified draft tokens, it does not know how many were accepted. The device knows both soon after sampling, and the next forward runs on the device. DeepInfer therefore lets the device complete the host’s one-step-old metadata.

6.2.2 The missing accepted length

Now let each request verify two draft tokens per step (nextn=2), so each step evaluates three positions. After verification, a request keeps its main token plus the accepted drafts. The host cannot know that number while scheduling step N + 1.

The scheduler reserves the maximum. When it schedules a request, it records the step’s query length as in flight (scheduler.hpp, line 726). The next step’s key length is the committed count plus in-flight positions plus the new query length (line 697). That is an upper bound [37].

Follow request 11. It had 31 committed positions before step N. Step N reserved 3 and step N + 1 asks for 3, so the host’s key length is 37. With drafts enabled, the C++ preparation subtracts the current query length, giving a base of 34 (zos.cpp, line 188). The device then applies the reference formula. For real row i with remap ri and query length qi,

ki′ = k base,i+qi− { nextn− ari,ri ≥ 0,

where ari counts the drafts accepted in the matched previous row, excluding the main token. Request 11 accepted none: 34 + 3 − (2 − 0) = 35. The synchronous reference agrees: 31 + 1 + 0 = 32 committed positions after step N, plus three new queries. Request 13 accepted both drafts, so its reserved length was already right: 36 + 3 − 0 = 39. The base exists so that the formula does not add q twice [40, 43].

The input tokens change too. A matched row’s first input is the token sampled in step N; the remaining inputs are the new drafts that step N proposed. Request 12 shows a further consequence. Its step N sample is the end-of-sequence token, number 2 here. The host learns this only when it post-processes step N, after forward N + 1 has been queued. Step N + 1 therefore evaluates request 12 anyway. Evaluation and publication are separate: the row can be computed, but its result will not be returned to the user. Section 6.4 follows that row to the end of its life.

The batch has 12 query positions, so the worker selects a captured graph for 16 positions and adds four padding rows. There are now eight metadata rows: four real requests with three positions each, and four padding rows with one position each. The script checks that the padding rows keep q = k = 1 and remap −1: the correction applies only to the first n_seq real rows. Section 6.5 explains the padding.

6.2.3 A query length chosen on the device

Chapter 8 adds a third unknown. With variable-length verification, the number of drafts each request verifies depends on confidence estimates from the previous sample. The host fixes only the step’s total query length; the device divides it among requests. Chapter 8 describes that allocation. Here only its dependency matters. The sampler’s host metadata needs the per-request lengths, which now exist only on the device. A non-blocking copy returns them to pinned host memory, and the host must wait for the copy’s event, d2h_evt, before updating that metadata (worker.py, lines 146–152).

The last row of lab 13 adds this case as a one-unit correction queued before forward. It runs after sample N and before forward N + 1 on the same stream. Its event is therefore complete soon after the host’s existing wait for sample N; the step lengthens by the correction’s device time, from 12 to 13 units. That result depends on the assigned durations. The code establishes only the order.

6.3.2 When the correction does not run

ZOS is on by default only for some engine types: NORMAL and COMPLETION, not PROMPT (engine_type.py, lines 16–17). EngineArgs applies that default with os.environ.setdefault, so an existing DEEPINFER_ZERO_OVERHEAD_SCHEDULING setting wins (arg_utils.py, lines 51–55). Prompt steps always post-process their own result in the same call; chapter 1 printed that branch. A prompt step can still post-process a preceding decode step, because that happens earlier in the call. Correction returns early when there is no previous state, when the previous step was a placeholder, or when no row matches (worker.py, lines 198–213) [44, 39, 7].

6.4 Last use, reuse and the cost of end-of-sequence

Request 12 sampled its end-of-sequence token in step N. Follow it through three consecutive decode calls:

  1. Call N queues the forward and the sample that choose the end-of-sequence token. The host has not read it.
  2. Call N + 1 schedules request 12 again and queues forward N + 1 with its row. It then post-processes step N, which marks the request finished and publishes its last token. Sampling for step N + 1 still includes the row.
  3. Call N + 2 begins with scheduling. free_finished_seqs removes the finished request from the running list and hands it on as finished (scheduler.hpp, lines 562 and 752–763). Forward N + 2 no longer includes it. Post-processing step N + 1 waits for its sampling event and skips the finished row (lines 905–913). pre_sampler_sync then releases its storage:

The trace assumes consecutive decode calls. A prefill step in between changes when the decode cleanup pass runs, so the release point needs a separate trace.

The extra row is the price of not waiting. Each finished request is evaluated once more after its last published token. As an illustration, suppose there are no drafts and each decode step produces one useful token. If answers averaged 200 tokens, one extra evaluation per answer would add about 0.5 per cent to decode rows, ignoring the first token produced by prefill. That figure is arithmetic, not a measurement. With drafts, both the number of normal decode steps and the number of positions in the extra step change. Chapter 5’s stale-result guard is the same idea applied to a request preempted while its step was in flight, and chapter 1’s final flush drains the one step that no later call will collect.

6.4.1 What makes a release safe

Chapter 4’s second lab released a block while a queued copy still needed it, and a new writer corrupted the copy. That lab did not prove that every release after submission is unsafe. The governing condition is narrower: a conflicting use by a new owner must follow the last access by the old owner. A host can meet it by waiting for an event. It can also rely on an order that is guaranteed some other way, such as two operations on the same stream. Allocator reuse, the lifetime of host objects and the publication of a result are different questions, and DeepInfer answers them differently. Table 6.1 lists the release points met so far.

The first row remains open. A complete argument must account for every access to the reused cache: eager forward, graph replay, draft execution, copies and zeroing, and any storage hooks. Graph capture uses its own stream with explicit waits (cuda_graph_runner.py, lines 100–137); that fact alone neither proves nor disproves safe runtime reuse. The release’s storage hooks are empty, so they say nothing about the unreleased service. Until that audit is done, the first row is a scoped inference from the inspected control flow [5, 41, 45].

6.5 Graphs constrain the input buffers

A CUDA graph records a fixed sequence of device operations, with fixed shapes and buffer addresses, so that the host can later replay it with one submission. Fewer submissions mean less host work per step, which lab 13 showed to be the limit on overlap. The cost is rigidity.

DeepInfer captures graphs for a list of batch sizes: powers of two up to an interval, then multiples of that interval, with a default interval of 8 (cuda_graph_runner.py, lines 41–51; environ.py, line 155). The largest size is max_num_seqs times 1 + nextn, and PROMPT engines do not use decode graphs (model_runner.py, lines 72–79). Selection uses total_q, the number of query positions, not the number of requests (cuda_graph_runner.py, lines 143–148). Chapter 2’s distinction between requests and positions decides which graph runs. The worker adds padding rows to reach the selected size (worker.py, lines 202–207). Lab 14’s 12 positions became 16.

The graph’s inputs must also be where it expects them. Under ZOS, the runner is built with device-side input storage (model_runner.py, line 78), and the graph data’s docstring says that source tensors share device storage in that mode (cuda_graph_runner.py, lines 26–31). The corrections in this chapter therefore write into buffers that replay reads. Correcting a host copy instead would require the host to read the previous result first, which is the wait ZOS was built to avoid [45].

We can now label each piece of state by the step that produced it, the event or stream order that allows the next read, and the condition that allows reuse. The next chapter spreads this work across devices, where a step must also wait for other devices.
