INSIDE DEEPINFERTHE WEB EDITION

CHAPTER 07

Put experts on several devices

Chapter 3 placed attention and a feed-forward transformation inside each model layer. We now open that second part. DeepSeek’s V4 models use many networks called experts in their MoE layers. For every token, a gate scores the experts and chooses a few. Each token therefore uses only part of the layer’s weights, but different tokens use different parts. When the experts are spread over many devices, tokens must travel to the experts they chose, and the results must travel back.

The question

How does DeepInfer send each token’s expert work to the devices that hold those experts and bring the results back? Why can one busy device limit the benefit, and how does the engine move experts to reduce that imbalance?

7.1 Dispatch, compute and return

A layer built this way is a mixture of experts (MoE). The gate gives each token a short list of chosen experts and a weight for each. The layer’s output is the weighted sum of the chosen experts’ outputs. DeepSeek’s design also has a shared expert that every token uses, without being chosen [28].

Each expert occupies a slot on one rank. The routing weights are fractions, so the distributed result can be compared exactly with direct evaluation.

The first run gives each token one expert. Dispatch sends each token’s value to the rank holding its expert. The receiving rank computes the result, and combine returns it to the token’s own rank. A token must carry its identity on the journey, or its result could not be put back in the right place. Four of six tokens chose A, so rank 0, which holds A and B, receives five of the six assignments.

The second run gives each token two experts with weights. A token now creates two assignments, possibly on different ranks. Each result is multiplied by its weight before it returns; the origin adds the shared expert’s output, computed locally, and the returned contributions. The script checks every token’s result against direct evaluation. Rank 0 receives 8 assignments and rank 1 only 4.

The third run moves B and C between ranks. Every token result is unchanged; only the work per rank and the number of assignments crossing ranks change. That is the freedom a placement policy uses.

The fourth run adds two slots, holding a second copy of A and of B. We now distinguish a logical expert, the function the gate chooses, from a physical expert, a copy of its weights in one slot. A copy is called a replica. A replica adds another place to compute A; it does not add an expert to any token’s choice. The lab picks a replica with DeepInfer’s rule, shown in the next section. Rank 0 and rank 1 now receive six assignments each, and the results are still unchanged.

7.2 Follow DeepInfer’s execution path

DeepseekMoE in v4_modules/mlp.py executes the layer; the neighbouring moe.py defines the parameter containers it receives. Its constructor fixes the slot arithmetic (lines 196–202): the number of physical experts is the number of routed logical experts plus the extra replica slots, and each rank of the expert-parallel (EP) group holds an equal share. An assertion requires the total to divide evenly [47].

The execution crosses several repositories, all within DeepSeek’s library stack. DeepGEMM, DeepEP and TileKernels supply kernels and communication; DeepInfer connects them to the model and the request loop. The boundary is concrete:

Boundary

Division of responsibility

Replica selection

DeepInfer supplies logical-to-physical maps and replica counts; the DeepGEMM or TileKernels gate chooses a physical copy.

Dispatch and combine

DeepInfer calls DeepEP’s EPBuffer with rows, weights, events and a load counter, and uses the returned handle.

Expert computation

DeepInfer selects the explicit or fused path and connects the shared contribution; DeepGEMM and TileKernels perform the kernel work.

Load balancing

The statistics window, policy call, weight shuffle and mapping updates are implemented in this repository.

The inspected calls and pinned dependencies establish these boundaries [47, 48, 55]. The model determines the routed expert functions and their selections. Extra physical copies are a deployment choice for serving uneven routed work, rather than additional logical experts required by the model.

to_physical_map lists the slots holding each logical expert, and logical_count says how many there are. On GPUs the gate runs in DeepGEMM’s bf16_mega_gate; otherwise it uses the TileKernels gate. Both are DeepSeek libraries maintained in separate repositories. At DeepInfer’s pinned submodule commit, DeepGEMM chooses a replica by

where token is the token’s index in its own rank’s batch. The source comment says the purpose: spread one logical expert’s tokens over its replicas, differently on every rank. The TileKernels version required by DeepInfer uses the same rule [52, 53].

The rule does not look at current load. It spreads tokens by their index, so replicas share work only approximately. In lab 15, A’s five assignments split two and three. The placement policy later in this chapter assumes an equal split; that assumption is an estimate.

Follow token (0,1) in the lab’s fourth run. Its value is 5 and its logical choices are A and C, each with weight 1∕2. The layout is ABC/DAB, so A’s slots are [0,4] and C’s only slot is 2. For A, the replica rule gives 23333 mod 2 = 1: the second copy, slot 4 on rank 1. For C it gives zero: slot 2 on rank 0. The equivalent row of topk_idx is therefore [4,2], paired with topk_weights [1∕2,1∕2].

7.2.2 Through the experts and back

dispatch hands the hidden states, slot indices and weights to DeepEP’s communication buffer [47]. Like the asynchronous work in chapter 6, the transfer runs on its own schedule. current_stream_wait makes the compute stream wait for its event before using what arrived. The results are the rows received by this rank, their weights and a handle. The handle carries the bookkeeping needed later: how many received rows belong to each local expert, used by the expert computation (line 596), and the routing information needed to send results home.

For our token, dispatch sends one row to rank 1’s local slot 1 (global slot 4) and one to rank 0’s local slot 2. The received weights follow those rows into routed_experts_forward; the handle’s psum_num_recv_tokens_per_expert describes their grouping by local expert. DeepInfer’s rows are hidden-state vectors; the lab uses the scalar 5 so that we can calculate the contributions by hand.

Where do the weights take effect? Not in combine. Inside the expert computation, the activation step receives them:

The shared expert runs on the token’s own rank. limit_num_sms lowers the number of streaming multiprocessors that its kernels may use by the number set aside for communication, so the transfers keep their share of the device (parallel_utils/userbuffer.py, lines 40–51). combine passes its output as bias (line 505): the shared contribution is added when the routed results arrive. In the scalar trace, A returns (2 × 5 + 1)∕2 = 11∕2 from rank 1 and C contributes (5 − 4)∕2 = 1∕2 on rank 0. The dispatch handle lets combine return the remote contribution to the original row on rank 0. The shared contribution is 5 + 10 = 15, supplied as bias in the explicit engine path. The final value is 11∕2 + 1∕2 + 15 = 21, the lab’s result for (0,1).

7.2.3 The fused path

The explicit stages are a readable account of the data movement, but they are not the only path. Lines 184–188 require the whole EP group to lie within one NVLink domain, a set of devices joined by a fast direct interconnect. They also require either a GPU platform or FP8 activations with FP4 weights, and a supported matrix-multiplication format. When these conditions hold, forward returns early through mega_moe_forward (lines 528–563).

That method still calls gate_forward, writing the choices into a symmetric buffer shared across the group. A single DeepGEMM call then receives the buffer, both expert weight matrices, the shared-expert weights when they are fused, and the load counter discussed below (line 555). The routing, expert work, shared work and load counting are all present; they are no longer separate Python stages. The README reports its decode benchmarks on 64 GPUs within one scale-up domain, the setting in which this condition can hold, but the book has not established which path those runs took [47, 1].

7.3 Why widen the expert group?

Figure 7.1 shows the arrangement the deployment Q&A describes for V4.1 decode. Attention runs with data parallelism (DP): each rank processes its own requests. The MoE stage runs with expert parallelism over the same ranks, with the DP size equal to the EP size. The Q&A reports decode groups of EP64 to EP128, calls this Wide-EP, and says that it substantially reduces per-step memory traffic in the expert part [2]. The released code supports other group sizes; these numbers are a reported production setting.

Chapter 2’s cost model explains the attraction. Take an illustrative layer with E = 256 routed experts, each token choosing k = 8, and B = 32 tokens per rank. These are teaching numbers, not V4.1’s configuration. With P ranks and no replicas:

Ranks P Experts per rank E∕P Mean assignments per expert PBk∕E
8 32 8
64 4 64

Holding the per-rank batch fixed, the wider group gives each rank fewer expert weight matrices to read per layer, and each matrix serves more tokens on average. In chapter 2’s terms, the expert computation moves towards higher arithmetic intensity. The comparison assumes every expert receives some tokens, the same model and the same hardware.

Two costs limit the gain. Each rank still sends Bk assignments and receives their results, whatever the group size, and in a wider group a larger share of them leave the rank. The step must also wait for the slowest rank. Lab 15’s second run had 8 assignments on one rank and 4 on the other. Those counts identify the busiest rank in the lab; it has no duration model. Kernel efficiency and communication also affect the time, so the counts do not establish step latency.

7.4 Use history to choose a placement

The engine reduces imbalance with expert-parallel load balancing (EPLB): it observes which experts were busy and periodically changes which slots hold which experts. Figure 7.2 shows the cycle.

7.4.1 Counting work

The counter appears in the MoE calls themselves: explicit dispatch passes the layer’s expert_count as cumulative_local_expert_recv_stats (line 474), and the fused call passes the same tensor (line 555). It has one entry per local physical slot and layer.

After sampling, DeepseekForCausalLM calls ExpertLoadBalancer.step (deepseek.py, lines 402–404). That method updates the rearrangement history when enabled, records load statistics and finally zeroes the counter. The rearrangement history is a ring of recent steps, the window. Every interval of eligible steps, it triggers _rearrange_experts [48].

The policy needs counts per logical expert across the whole group, not per local slot. First, _rearrange_experts selects this rank’s mapping and allocates space for logical counts:

Full ranks were excluded on line 62, and argmin breaks ties towards the lower rank. The result in the lab is AAD/ABC, with an estimated score of 68. The starting layout, ABC/DAB, which gives the two extra slots to A and B, scores 70. These scores are estimates in the policy’s own model. The policy divides an expert’s load equally among its copies, whereas the gate’s index rule splits them approximately. The algorithm is greedy, so it does not guarantee the best placement. The score leaves out communication, kernel efficiency and the cost of moving weights. A difference between 70 and 68, or between 40 and 20, is not a measured speed-up.

7.4.4 Compare two DeepSeek placement policies

DeepSeek also published a standalone EPLB implementation. At the fixed commit d52c72d, it already separates logical experts from physical replicas, allocates redundant copies and packs them into equal-capacity device groups. Its entry point returns the same three kinds of map/count tensors. Its README leaves load prediction to the caller and suggests a moving average of historical statistics [54]. The useful comparison is therefore how the two policies represent and use load, not whether replication first appears in DeepInfer.

In the standalone code, replicate_experts chooses copies and balanced_packing places them. The entry point is rebalance_experts. Compare these with the two DeepInfer functions just read [54, 49].

The input difference can change a decision. Consider two experts with loads (10,0) in one step and (10,18) in the next, and one spare slot. If the caller supplies totals (20,18) to the scalar policy, it copies A. Keeping both steps, a copy of A gives per-step maxima 5 and 18, summing to 23; a copy of B gives 10 and 10, summing to 20. DeepInfer’s replica score therefore chooses B. The third case in lab 16 calls DeepInfer’s policy with this history, three physical slots and one slot per rank. 7.5 Make the new placement take effect

7.5.1 The slot budget is fixed

Extra slots cost memory: each holds a full copy of one expert’s weights in every MoE layer. The number is fixed when the model is built. The loader reads a requested minimum from DEEPINFER_OVERRIDE_NUM_EXTRA_EXPERTS, which defaults to zero, and resolve_num_extra_experts rounds it up so that the total divides evenly among EP ranks (model_loader.py, lines 83–107; eplb/__init__.py, lines 21–28). The example setup requests at least 32 (examples/_config.py, lines 77–79). As an illustration, 256 routed experts plus 32 requested extras make 288 slots; at EP64 the engine adds 32 more so that 320 = 64 × 5. The Q&A reports, for decode, one extra slot per GPU before rounding [51, 48, 17, 2].

A later policy call does not add slots. It only chooses which logical experts occupy them. Comparing configurations with different slot budgets must therefore charge the extra weight memory: device memory that chapter 4’s block pool could otherwise use.

The three tensors are updated in place. The per-layer state that the gate receives is a view of those same tensors (lines 346–376), so the next forward pass reads the new mapping without any other hand-over. The weights must already be in their new slots when that happens, which is why the shuffle comes first. The rank-0 metrics path synchronises the device around the operation and logs its elapsed time (lines 226–228 and 280–288) [48].

Moving weights has its own hazard. Suppose slot 2 should receive the expert that slot 5 holds, while slot 5 should receive slot 2’s expert. Copying one directly into the other would destroy a source that is still needed. The general point-to-point shuffle avoids that by staging. Copies within a rank and transfers from other ranks both write into separate receive buffers first (shuffle.py, lines 107–138). Only after every transfer has completed does it write the changed slots:

Unchanged slots are skipped. A changed slot takes its new weights either from its own staged copy or from the buffer that received that expert from another rank. When the whole group lies within one NVLink domain, the intranode path instead copies each rank’s weights into a shared mirror, one layer at a time. Two barriers bracket the mirror refresh; their comments say, in the author’s translation, “wait for every rank to finish reading the previous layer’s mirror” and “wait for every rank’s mirror to be ready” (lines 192–195). Reads then come from mirrors, or from a slot that has already received its new weights [50].

Apply the general shuffle to the lab’s actual transition, ABC/DAB to AAD/ABC. Global slot 2 on rank 0 must change from C to D. D currently lives in global slot 3, rank 1’s local slot 0. Rank 1 sends those weights into rank 0’s receive buffer at local index 2. Once the transfer completes, the final loop copies that buffer entry into rank 0’s weight slot 2. Meanwhile C must move from old slot 2 to rank 1’s slot 5. Staging both transfers preserves C before slot 2 is overwritten. Figure 7.3 shows these two transfers; the other changed slots use the same shuffle.

Only after the shuffle is queued does the engine queue the three tensor updates. For this layer, physical_to_logical_map becomes [A,A,D,A,B,C]. The valid entries in logical_to_physical_map are A: [0,3,1], B: [4], C: [5], D: [2], with logical_count [3,1,1,1]. A’s list is in the order returned by the policy, not sorted slot order; the replica formula indexes that list. These are the lab’s actual outputs.

On the next forward pass, consider token (0,2), which selects D in lab 15. D still has one replica, so its replica index is zero. The gate now reads logical_to_physical_map[D,0] as 2 rather than 3. Dispatch therefore sends that assignment to rank 0 rather than rank 1, and the destination slot now holds D’s weights. The logical computation is unchanged; its location has changed.

7.5.3 When rearrangement runs

Rearrangement is off by default. DEEPINFER_EXPERT_REARRANGEMENT_STEP_INTERVAL defaults to zero, and _update_rearrangement returns early in that case (environ.py, lines 115–117; eplb/__init__.py, lines 147–148). For an EP group with more than one rank, step still calls _update_load_balance_stats and clears expert_count (lines 131–138). Load statistics, including their periodic collective, remain active when rearrangement is off; this is the statistics flush discussed in chapter 2. When it is enabled, the window must lie between one step and the interval (lines 106–111), and the first rearrangement comes after a quarter of the interval, to correct start-up imbalance sooner (lines 121–123). A normal engine leaves prefill steps out of the window unless a separate setting asks for a rearrangement straight after prefill (lines 83–84 and 149–159). The example setup uses a three-step window and, when EPLB is enabled, a 30-step interval (examples/_config.py, lines 80–83) [30, 48, 17].

The deployment Q&A reports very different production settings: a 100-step window and a 1,000-step interval for prefill, and 1,000 and 10,000 for decode. It reports a ratio of slowest to mean rank load of 1.074 and 1.045 for two prefill configurations and 1.090 for decode [2]. Those are DeepSeek’s reported measurements; this book has not reproduced them.

Both settings reflect a trade. A placement is chosen from the past, so it lags a workload that changes. Moving weights takes time on every rank. As a teaching model only: if a rearrangement costs R seconds and saves s seconds per step for the next M steps, it pays when sM > R. Long intervals bet that expert popularity changes slowly. The rank-0 log already records rearrangement time, which supplies an observation of R. This book has not run the engine to obtain that value or measured the subsequent saving s and how long it persists. Choosing M needs those measurements.

We can now follow a token’s expert work from the gate to another rank and back, and follow the counts it leaves behind into a new placement. These choices affect the cost of a forward pass. The next chapter asks which draft positions are worth evaluating at that cost, allocating a verification budget across requests using predicted useful output and measured step times.

7.6 Experiments to try next

  1. In labs/15_dispatch.py, give token (1,1) the choices A and D. Predict the per-rank assignments in runs 2 and 4 before running the script.
  2. Change the replica rule in the lab to always pick the first copy. Which rank becomes busiest in run 4? What does the index rule buy, and what can it not guarantee?
  3. In labs/16_placement.py, add a third step in which only A and C are busy. Does the policy still choose AC/BD? Compute both scores by hand first.
  4. Give the skewed history four slots per rank. How many replicas does each expert receive, and does the score improve? Relate the extra slots to weight memory.
  5. Using the teaching model sM > R, list the quantities you would need to measure to choose a rearrangement interval, and where in DeepInfer you would record each one.
