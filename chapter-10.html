CHAPTER 10

Different correctness contracts

The previous chapter separated two questions: whether mask and compact compute the same truncated model, and whether that model is close enough to a full prefill. A passing test answers the question encoded in its assertion. Changing the question can change the verdict without changing the engine.

The question

A row contains 1016,−1016,1. Why might its sum change when an unrelated row joins the batch? If two computations pass a check whose threshold is zero, have they necessarily produced equal values?

BASH
python3 labs/21_equality.py

The experiment makes the reduction order depend on the number of rows. It then keeps that order fixed, and finally tries two other checks:

OUTPUT
row-count-dependent: single=1, batched=0
row-count-dependent: masked=0, compact=1
fixed order: A=1 in every layout; 6 subset/order checks
adjacent float32 inputs: equal=False, abs diff=1.16415321827e-10
exp(d)-1-d metric=0; zero does not establish equality
logprob lists differ; both perplexities=7.389056099
Saved output · results/21_equality.txt

The unrelated row changes the first result from 1 to 0. Fixing the order removes that difference. Yet a numerical difference metric can still return zero for unequal inputs, and two different logprob lists can have equal perplexity. These are three different observations, not three ways to prove the same claim.

Scope and order. We first explain the reduction, then follow DeepInfer’s batch-invariance flag into its libraries. Golden tokens let us compare computations along a fixed history. A second experiment separates repeatable random draws from a correct output distribution. Finally, we trace how grammar masks and matcher state constrain speculative output. The released tests supply the questions and assertions throughout; this chapter inspects them but does not run their model workloads.

10.1 Equality needs a fixed computation order

In exact arithmetic both ways of grouping the row give 1. In Python’s usual binary64 arithmetic, adding 1 to 1016 loses the 1. The lab’s single-row path adds from left to right:

(1016 + (−1016)) + 1 = 1.

Its multi-row path gives alternating entries to two lanes. The first lane adds 1016 + 1, the second contains −1016, and the lane totals add to 0. A reduction combines several values into one; its grouping is part of the numerical computation.

Here is the entire layout-dependent rule. Masking keeps the batch shape but skips unwanted outputs; compacting removes those rows before the call:

Listing 10.1. Choose the lane count from the batch shape.
PYTHON
19def reduce_rows(rows, active, fixed=False):
20    lanes = 1 if fixed or len(rows) == 1 else 2
21    result = {}
22    for name, values in rows:
23        if name in active:
24            partials = [left_sum(values[lane::lanes]) for lane in range(lanes)]
25            result[name] = left_sum(partials)
26    return result
27
Book lab · labs/21_equality.py · lines 19–27

Neither operation changes the retained row’s values. Nevertheless, two physical rows select two lanes even if only one output is wanted. One compact row selects one lane. With fixed=True, both calls use one lane and agree. The lab checks all six combinations of nonempty retained subsets and row orders for its two-row input, comparing masked and compact calls against a direct sum.

This isolates one cause of a batch-dependent result. An engine also has to align dtypes, fused operations, kernel choices and the visible attention keys. Removing query rows can preserve the remaining computation when rows are independent in those respects. Removing keys from a retained query changes its mathematical input, as chapter 9 showed. No choice of addition order can undo that change. Figure 10.1 sets this comparison beside the other two execution changes this chapter tests.

We will distinguish four kinds of claim. An exact comparison requires equal observed values. A tolerance check admits a specified difference under a specified metric. A distributional check asks whether sampled outputs follow the intended probabilities. A task or format check asks whether an answer satisfies a requirement, such as a grammar. A valid format does not establish a factually correct answer.

Several released comments call direct comparisons “bitwise”. We will state the comparator: Python == and torch.equal compare numerical values, not raw byte strings. For example, numerical equality does not distinguish positive and negative zero. More importantly for this chapter, a zero threshold on a computed metric need not even establish value equality. We return to the lab’s counterexample when we open test_kl.py.

10.3 Golden tokens hold the trajectory fixed

Suppose two runs disagree at token 7. By token 8, their histories differ, so their model scores need not agree even in exact arithmetic. To locate the numerical difference, a test can force the same token history while continuing to compute the model’s probabilities. This is teacher forcing. DeepInfer calls the forced sequence golden_token_ids.

The batch-invariance test first generates a batch of 64 requests. It then replays each request alone with the batched output as its golden sequence:

Listing 10.5. Hold the trajectory fixed while changing the batch.
PYTHON

The helper _get_result collects token IDs, their logprobs, and the top-5 IDs and logprobs. The assertion compares the whole tuple. However, equality of the output token IDs is imposed by the override. The substantial numerical check is whether the model assigns the same logprobs and top-5 results along that history. It is not a comparison of two independent stochastic draws [77].

A golden value of −1 means no override. Otherwise, the candidate becomes the golden token and acceptance becomes the test “draft equals golden”. The prefix calculation then prevents a request from accepting drafts beyond its first blocked row. For a golden continuation [a,c] and drafts [a,b], the first draft matches, the second does not, and the output still follows [a,c]. The model’s stochastic acceptance probabilities did not decide that trajectory. This is why a golden-token test is useful for numerical comparison and unsuitable as evidence that rejection sampling preserves a distribution. Also keep these testing tokens separate from DFlash’s leading “golden” input: chapter 8 used that name for a committed token anchoring proposal generation.

10.3.3 Decode versus prefill: inspect the metric

test_kl.py uses MTP 5, context parallelism 2 and expert parallelism 8, with image input and batch invariance enabled. Its text tokens and golden continuation are drawn uniformly from non-special tokens, not from the model distribution. Sampling uses temperature 0.5 and top-p 0.95. The first pass decodes that continuation. The second appends it to the prompt and obtains its logprobs through prefill. This holds the history fixed while changing how it is computed.

The compared values are processed logprobs. Temperature changes the scores, top-p keeps a nucleus of high-probability tokens, and the remaining tokens receive zero probability. The sampling reference shows the order:

Listing 10.7. Transform the logits before reporting log probabilities.
PYTHON

210apply_top_p_top_k_ref(logits, transform_inputs.top_ps, transform_inputs.top_ks)
211logprobs = torch.log_softmax(logits, dim=-1)
DeepInfer · deepinfer/model_executor/layers/tilelang_ops/fused_sample.py · lines 209–211

The top-p helper replaces excluded logits with −∞, so their logprobs stay −∞. Prompt logprobs use the same request settings: csrc/engine/prepare_sample.cpp, lines 186–188, copies temperature, top-p and top-k into the prompt arrays. The prompt-logprob helper passes those arrays to fused_sample before looking up each prompt token [77, 59].

The original prompt’s logprob lists are compared directly. The continuation’s logprobs are converted to float32 tensors and passed to cal_diff; the test accepts its fourth field at a threshold of zero. Before either comparison, it replaces −∞ with −9999. Those transformations are part of what the test checks. If a token lies outside both nuclei, both values become the same sentinel, irrespective of their excluded logits. Such a position records agreement on exclusion, not agreement between finite logprobs. If nucleus membership differs between the runs, that normally produces a sentinel-versus-finite discrepancy.

Uniformly chosen tokens could make these exclusions common when the model’s nucleus contains few vocabulary entries. The fraction depends on the model and histories; it has not been measured here, and the test does not report it. To assess numerical coverage, record positions excluded on both sides, positions retained on both sides, and membership disagreements before replacing infinities. Finite-position differences and exclusion agreement answer different questions.

Two comparisons help locate this limitation. YOCO L2 uses temperature 0.5 and top-p 1.0, leaves top-k disabled and asserts that DEEPINFER_SAMPLER_FORCE_TOPK is zero: there is no nucleus or top-k truncation in that setup. The batch-invariance test instead obtains its golden tokens by sampling the batched run, rather than uniformly choosing vocabulary entries. Its chosen tokens therefore come from that run’s retained distribution; the single-request replay must match their logprobs and top-5 results. Neither contrast makes the selected probabilities an independent oracle for the whole model [75, 77].

The continuation comparison has a second limitation, in the metric itself:

Listing 10.8. A field named kl is computed from chosen-token logprob differences.
PYTHON
4def cal_diff(x: torch.Tensor, y: torch.Tensor) -> tuple[float, float, float, float]:
5    if torch.equal(x, y):
6        return 0.0, 0.0, 0.0, 0.0
7    x, y = x.double(), y.double()
8    rmse = ((x - y) * (x - y)).mean().sqrt().item()
9    cos_diff = 1 - 2 * (x * y).sum().item() / max((x * x + y * y).sum().item(), 1e-12)
10    chebyshev_dis = (x - y).abs().max().item()
11    kl = ((torch.exp(x - y) - 1) - (x - y)).mean().item()
12    return cos_diff, rmse, chebyshev_dis, kl
DeepInfer · deepinfer/testing.py · lines 4–12

Write d = x − y. The last field averages ed − 1 − d over the selected tokens. A KL divergence between two categorical distributions would require summing over their token probabilities with the appropriate weights. This expression is a discrepancy measure on the supplied logprobs; its name does not make it that distributional divergence.

In real arithmetic, ed − 1 − d is non-negative and zero only at d = 0. Floating-point subtraction changes the conclusion. Lab 21 uses adjacent float32 values, both exactly representable in Python’s binary64 floats:

x = −0.0010000000474974513,y = −0.0009999999310821295,|x − y| = 2−33.

The lab evaluates the same scalar expression and gets zero. The original PyTorch helper also returns zero for these inputs on CPU despite torch.equal being false. The first return branch is sufficient for zero, but it is not necessary. To assert exact value equality, compare the values directly; to allow a tolerance, choose and state a metric that measures the intended difference.

This comparison completes part of chapter 5’s recomputation story. Rebuilding decoded history through prefill should reconstruct compatible representations and probabilities. The test probes that boundary for its selected inputs and settings. It does not actually preempt and resume a request, and its zero metric does not prove identical continuation. Sampling state, auxiliary state and the cache must also be compatible. Nor does this test enable chapter 9’s truncated-prefill mode.

10.3.4 Two other baselines

YOCO L2 compares mask with compact under batch invariance, fixing the golden trajectory and checking the other relevant settings. It directly compares chosen logprobs, top-k IDs and logprobs, and optional DFlash confidence values. The context-parallel derivation comment in deepinfer/model_executor/input_metadata/yoco.py, lines 136–139, explicitly points to an end-to-end equality check. Neither a local derivation nor agreement between these two truncated modes measures their error against full prefill. That remains chapter 9’s separate quality question.

The offline-inference test uses a different baseline: stored decode perplexities in tests/models/offline_decode_ppl.json. It checks the current run against those scalars, rather than comparing two fresh runs. The baseline is tied to the platform, workload and parallel configuration: NVIDIA uses EP 4 / CP 2; Ascend uses EP 16 / CP 8. Both have two data-parallel ranks. Changing that configuration requires a new baseline.

For chosen-token logprobs ℓ1,…,ℓn, perplexity is exp ⁡ (−∑ ⁡ iℓi∕n). Lab 21 compares [−1,−3] with [−2,−2]. Both give e2, although neither token’s logprob agrees. Exact equality of an aggregate is an aggregate regression check, not tokenwise equality.

10.4 Repeatable and correctly distributed are different claims

With seed 11 at position 7, a fresh target draw produces token 1; the accepted draft produces token 0. Under ideal uniform draws each rule still has exactly the distribution (1∕2,1∕2). No end-to-end test of that complete recipe was found in the inspected tests/models/ inventory: none sets seq_seed. Embedded sampler and RNG kernel tests are different checks. The evaluation driver supplies per-sample seeds but initially sets varlen to 1; its later –env loop can override that value. Its default setup is therefore not the README’s recipe. Seeds alone, or the helper’s repeatability docstring, do not establish that those evaluation runs are repeatable [79].

10.4.3 Test the probabilities, not just the seed

test_sampler.py asks whether the sampled tokens agree statistically with their reported probabilities. It uses MTP 5 and four settings (T,top-p) = (0,1),(1,0.95),(8,0.95),(1,1), with 128 trajectories per setting and up to 2,048 output tokens per trajectory [80]. It does not force a golden continuation.

A categorical sample is not a uniform number. A randomised probability integral transform (PIT) turns it into one under the target distribution. Order the tokens, give token x an interval of width px, and let F(x) be the interval’s upper end. Given the sampled token, draw an independent uniform U and form

Z = F(x) − Upx.

If token x is chosen with probability px, that probability is spread uniformly over an interval of the same width. The intervals together fill [0,1] uniformly. The construction works conditionally on each token’s history; the probabilities can change between positions.

DeepInfer calls the upper endpoint sum_smaller_probs. It sorts by ascending probability, breaking ties by column index, and includes the sampled token. Its reference calculation makes the tie rule explicit:

Listing 10.13. Build an inclusive CDF in probability order.

41mask_equal_before = (logprobs == pivot) & (col_idx <= sample_results.unsqueeze(1))

KS measures the largest gap between the sample’s cumulative distribution and the uniform CDF. The helper turns that gap into an approximate p-value using an asymptotic formula with a finite-sample correction. A p-value describes how unusual such a discrepancy would be under the null model; it is not the probability that the sampler is correct. The helper returns a p-value under the name ks_quantile. A second KS check compares those trajectory-level values with a uniform distribution.

all_pv uses the whole trajectories. The test also prints next1_pv, based on tokens after steps marked by draft_tok, but does not reject on that value. The filtering is consequential: if any position has ssp− p < −0.01, the helper returns None and that whole trajectory is omitted, not failed. An inclusive CDF should satisfy ssp ≥ p; the tolerance filter can therefore discard evidence of the very probability inconsistency being investigated. The helper also omits missing or non-finite data and non-positive probabilities, then clips the surviving PIT values to [0,1]. If fewer than two valid trajectory-level values remain, the aggregate is unavailable and the test fails. Otherwise, the aggregate may pass despite discarded trajectories.

Passing means this finite test did not detect a discrepancy at its threshold. It cannot prove exact distributional equality or exclude chapter 8’s small, deliberate residual penalty. There is another uncovered claim: PIT compares samples with the distribution the engine reports after its transformations. If temperature or top-p is applied wrongly, both sampling and the reported probabilities could use the same wrong transformed logits and still pass. An independent check of the transformations would be needed to detect that error. This test also does not enable structured output, which adds another transformation of the distribution.

10.5.1 The mask belongs to a tentative history

The grammar compiler and matcher are provided by the external XGrammar library, pinned as xgrammar==0.2.2. DeepInfer’s wrapper in deepinfer/structure_output/matcher.py owns trigger progress, bound-token state, EOS bookkeeping and rollback. Unlike the independent DeepSeek kernel repositories, XGrammar is an external project supplying grammar machinery. DeepInfer supplies the integration with speculative requests [81].

The wrapper’s rollback capacity is nextn+2. Its rollback method restores the inner matcher’s state and the wrapper’s trigger/EOS/bound bookkeeping. The extra two positions are an implementation allowance; the constant alone does not establish why precisely two are required. What matters for this path is that tentative advancement and restoration stay paired.

10.5.2 Failure ends the request

A compilation future can time out or fail. Its wrapper returns an aborted matcher. When the engine enqueues a request with such a matcher, it marks FINISHED_SO_FAILED in deepinfer/engine/llm_engine.py, lines 621–622. During sampling, a missing or aborted matcher sets so_status to −1; runtime exceptions also mark it aborted and set that status. The scheduler closes the path by checking the stored status:

DeepInfer · csrc/engine/scheduler.hpp · lines 976–980

The two appended zero IDs are the scheduler’s failure bookkeeping. The branch marks the sequence failed instead of continuing unrestricted generation. The preceding comment explicitly says to consult the stored status, not only the report for this step: a step with no active structured-output work may report no status (author’s translation). A missing report must not erase an earlier failure.

This is also the boundary of chapter 5’s preemption discussion. The scheduler sets so_blocks_recompute whenever structured-output status is nonzero. Such a request terminates on preemption even if ordinary requests would be recomputed. Restoring KV would not, by itself, restore the matcher and its trigger history. Reconstructing that state would be a requirement for a new recovery implementation, not a feature present in this release. The speculative rollback above is implemented; preemption recovery of the matcher is not.

10.5.3 Where the constraint begins, and what the tests cover

A trigger can leave an initial part of the output unconstrained. Once its token sequence matches, the grammar takes over. A bound token has a more specific meaning: if it fires while the trigger is pending, the wrapper forces the remaining trigger tokens and then enters the grammar. It is not an ending delimiter that releases the constraint. These rules live in accept_token and fill_vocab_mask, with their state included in rollback.

The released structured-output example supplies three prompts asking for incompatible formats, then requests a regex, a JSON schema and an EBNF grammar. All use temperature zero. It requires nonempty output, a normal stop finish reason and a final EOS token before decoding the text.

The format checks are explicit:

The sampling KS test does not use structured output, so its result cannot fill that gap.
