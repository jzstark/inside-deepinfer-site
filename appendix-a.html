APPENDIX A

Compression and indexing

Chapter 3 followed a sliding window into attention; chapter 4 allocated blocks without explaining their compressed rows. Here we follow the other read path: completed compressed KV, a smaller index used to select rows, and the temporary state needed to produce the next row.

The question

If two token positions produce one compressed row, what happens when a prefill chunk ends after the first token? Can a later six-position verification step write all its inputs into a two-entry compression ring?

BASH
python3 labs/26_compression.py
OUTPUT
C2 rows (before BF16/norm/RoPE): [('6', '8'), ('8', '3'), ('3', '5')]
Chunks [0,1), [1,4), [4,7): valid/reserved rows [(0, 1), (2, 2), (1, 1)]
Pending token positions: [6]
Six-position decode: ring 7 preserves every completed pair
Ring 6 corrupts first pair: ('42/5', '8')

Default C2 state payload: 7 * 2 * 512 * 4 = 28672 bytes

Seven inputs produce three completed pairs and one pending input. Splitting the inputs into chunks of lengths 1, 3 and 3 does not change those pairs. A six-entry ring, however, lets the last new write overwrite the first pair’s old input. Seven entries preserve it. Compression reduces the completed cache; it still needs live state between steps.

Scope and order. We first explain the gated mean and its boundaries, then follow V4Attention through the compressor and indexer to the final attention read. A second experiment separates scoring, candidate restriction and address conversion. Finally, we account for bytes and distinguish the objects shared across layers. The case is a sparse C2 layer that owns its main KV and index-K, without YOCO compaction or CP sharding; later sections identify where those other paths differ.

A.1 A pair is complete only at its boundary

There are two kinds of compression in this discussion. MLA compresses a feature vector, as chapter 3 explained. C2 combines two token positions into one row. It does not halve the number of channels in that row. C1 keeps one row per position. The released Compressor accepts only ratios 1 and 2 and rejects the optional compress_overlap and use_ape settings [87].

For latent component d, the C2 operation over positions 2j,2j + 1 is

zj,d = ∑ t=2j2j+1 exp ⁡ (st,d) exp ⁡ (s2j,d) + exp ⁡ (s2j+1,d)vt,d.

The score s is a learned gate; v is the projected latent. Each channel has its own weights over the two positions. This is not attention over the whole context, nor an unweighted average. In v4_modules/mla_attn.py, SoftmaxAPEGatedColumnParallelLora constructs an A projection for values and a Gate projection for scores. Its name retains APE, although the runtime rejects that option. The single-position C1 softmax is one, so C1 needs no Gate [87].

The first lab pair has values (0,10) and (8,2). It substitutes positive integer weights (1,3) and (3,1) for the exponentials. The result is (6,8): the second token dominates channel zero, while the first dominates channel one. Fractions let us check this mathematical operation exactly. They do not reproduce floating-point exponentials or BF16 rounding.

The lab implements that mean with rational weights:

C1 receives BF16 and no compression state. Its optional gather restores CP’s input ordering. C2 receives FP32 score/latent pairs and requires state. The following branch calls the prefill or decode helper with the same ratio. These helpers return BF16 rows before the compressor’s normalisation and RoPE.

A.1.1 Chunk boundaries and placeholder rows

Let s be the first new token position and e the exclusive end of a chunk. For ratio r, the number of newly completed rows is

nc = ⌊e∕r⌋−⌊s∕r⌋.

The prefill reference iterates exactly those compressed indices. If a pair began before s, it reads that input from the state ring; otherwise it reads from the current projection. It subsequently retains recent score/latent pairs in the ring for later chunks [88].

For [0,1), no pair is complete. For [1,4), pairs (0,1) and (2,3) finish: position zero must survive the first chunk. For [4,7), only (4,5) finishes. Position six remains pending. Lab 26 tries every choice of cuts between the seven inputs and compares the completed rows and pending suffix with processing the whole sequence.

Physical output shape is not the valid-row count. The prefill metadata reserves max ⁡ (1,nc) rows per request, even when nc = 0. Its placeholder has position zero and store slot −1; the reference compression output is zero-filled there. Decode instead reserves one output row per query position, with zero output and no valid store slot for a position that does not complete a group. The C++ builder implements these conventions in prepare_tensor_input_v4.cpp:46–91. A placeholder is not an extra cached token [89].

A.2 Temporary state must survive speculative writes

A C2 cache row cannot replace the score and latent of an incomplete pair. The live ca_state stores both, in FP32, with shape

[state slots,S,2,latent dimension].

The axis of length two is score versus latent, not K versus V. ca_cache holds completed compressed KV in paged blocks. Their lifetimes and byte formats differ.

The decode reference writes every new position before computing completed rows. Its assertion states the required capacity:

For a group of r positions and up to qmax ⁡ new positions per state slot, retaining r − 1 old inputs alongside all new inputs requires S ≥ r + qmax ⁡ − 1. This is the same write-before-read hazard encountered with SWA, applied to a different ring.

In the lab, position zero is old; positions 1 through 6 are written in one step. With S = 6, position six takes position zero’s slot before pair (0,1) is read. With S = 7, no required input is overwritten. The incorrect first component becomes 42∕5, rather than 6. No future position belongs in that pair, even though it has already been written to memory.

With the default nextn=5, the backtracking allowance is at least six. For C2 the default ring is 2 + (6 − 1) = 7, not the SWA ring’s 134. The model configuration selects KProject with attn_index.use_kproj=True. The cache engine therefore leaves ica_state=None on this V4.1 path. This is a model-driven requirement. A block allocator alone cannot decide that the index keys derive from the main compressed latent, that C1 needs no pending pair, or that a consumer layer reuses another layer’s cache. Those decisions come from the model configuration and its runtime adapters.

A.4 Select rows, then translate their addresses

An indexer makes a cheaper scoring pass before main attention. The runtime describes its score for key kj as

Ij = ∑ hwh max ⁡ (0,qh ⋅ kj).

These are learned index queries and head weights, not the main attention softmax probabilities. ReLU means max ⁡ (0,x). DeepGEMM computes the logits; DeepSelect supplies the imported topk. Their kernel internals remain outside this walkthrough [90].

A.4.2 Candidate blocks are another restriction

Some layers first reduce index scores by candidate block, using a maximum, and select blocks for later layers to search. This grouping is distinct from the allocator’s 128-token page. In the lab, two index keys form a candidate block: block scores are 6 and 3. Retaining only the first block changes token top-2 from [1,2] to [0,1]. Thus top-k within candidates need not equal top-k over all valid keys, even with exact arithmetic.

The runtime’s candidate consumer accepts block sizes 8 or 16 in compressed-row units and imposes further width constraints; the lab’s block size two and single retained block are deliberately smaller teaching values. A source layer fills block_candidate_idxs; a consumer computes logits only within that set, then restores compact candidate offsets to logical row indices. Comparing this model with unrestricted attention would require a model-quality check, not merely equality between two implementations of restricted top-k [90, 91].

Prefill limits the size of its intermediate score matrix with compute_chunk_size. It derives the row width from either the full compressed context or the candidate set, applies the memory budget, rounds to multiples of eight and caps the chunk at 8,192 queries. That is a temporary logit-storage budget, not the number of keys finally selected.

A.4.3 The same logical row has two physical representations

For prefill, _load_prefill_kv gathers keys into a concatenated sequence buffer. Top-k adds the request’s ks offset, or restores candidate indices with that offset. With base 10, logical rows 1 and 2 become 11 and 12.

Decode keeps paged storage. With B original-token positions per allocator block, a ratio-r cache has Bc = B∕r compressed rows in that block. Logical row j maps to

slot(j) = block table[⌊j∕Bc⌋]Bc + (j mod Bc).

A.5 Count rows, payloads and owners separately

C2 halves the completed row count relative to C1. Low precision separately changes each row’s byte count. The index format specifies 128 FP4 elements and one one-byte UE8M0 scale per 32 elements:

The same file describes main formats. Here E2M1 and E4M3 name floating-point encodings; UE8M0 is the unsigned exponent scale encoding. The relevant accounting is payload bits plus the stored scales:

Cache format Data plus scales Bytes per row
Main/SWA FP8 512 + 512∕32 528
Main FP4 512∕2 + 512∕16 288
Index FP4 128∕2 + 128∕32 68

The main FP4 format uses one E4M3 scale per 16 values; its scale format differs from the index format. Main/SWA caches interleave data and scales within each row, whereas the index cache uses block-wide data and scale sections. The 68-byte figure is a logical per-row byte budget, not a claim that each physical index row is laid out as 64 immediately adjacent data bytes followed by four scales. Alignment and shared ownership affect total allocation [24, 90].

A 128-position C2 block has 64 completed-row slots. An owning main cache uses 64 × 528 = 33,792 payload bytes with FP8, or 18,432 with FP4; an owning index cache uses 64 × 68 = 4,352. The cache engine rounds regions to its alignment requirements and does not allocate another copy for a sharing consumer. The live 28,672-byte compression-state example is a separate per-request allocation. These equations explain chapter 4’s rows without claiming a measured reduction in model error or end-to-end latency.

A.6 Sharing has several meanings

Chapter 9 separated YOCO’s shared hidden state from segmented sharing. Here are the latter’s distinct objects:

layer_kv_map

Main compressed KV

layer_index_k_map

Index keys

Score its own queries and choose indices

layer_index_module_map

Selected top-k indices

layer_candidate_source_map

Candidate block set

For a four-layer teaching example, main-KV sources might be [0,0,0,0], index-K sources [0,0,2,2], and index sources [0,1,2,3]. Each finer segment lies inside a coarser one. An index-K source cannot project from a main KV belonging to a different segment. The topology checks this refinement:

This is only an example of valid map nesting, not a replacement model configuration. Other checks require compatible layer settings, preceding source layers and a fresh KV source at the YOCO boundary. A.7 Experiments to try next

The labs check rational compression, state lifetime and index/address arithmetic; they do not establish accelerator equivalence or acceptable generation quality. The released compression tests compare device outputs with a tensor reference and check state tensors. We inspected those assertions without running the tests.

  1. Change the first pair’s weights so each channel has equal weights. Which outputs become ordinary averages? Keep the chunk checks unchanged.
  2. Explain why a zero-valid-row prefill chunk still reserves an output row. Which metadata prevents that placeholder from becoming a real cache entry?
  3. For C2 with at most four new positions, derive a sufficient compression ring size and construct the write that would break a smaller ring.
  4. Give an example where restricting candidates preserves token top-k, and one where it changes it. What would a model-quality evaluation need in addition?
  5. Trace one selected compressed row through ica_cache, top-k, the block table and ca_cache. Which steps change values, and which only change addresses or the set of rows read?

The reading path distinguishes pending state, completed KV and selection keys. Use those distinctions to locate the next reader of a row and check its validity.
