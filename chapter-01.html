CHAPTER 01

A generation loop

Suppose a function takes a list of integers and returns a score for each possible next integer. You can use it to extend the list: call the function, choose an integer, append it and repeat. This is enough to describe the outer loop of text generation.

Running that loop for many people raises further questions. Which work can be reused? Which requests should run together? When can their memory be released? Four small programs give us the tools to follow a real request through DeepInfer. We will trace admission, scheduling, execution and result ownership, then explain why an empty scheduling queue does not end all of the engine’s work.

The question

What must we add around a prediction function to serve several requests? Watch three things: which token the next call needs, which work survives a call, and which request gets the next free slot.

Figure 1.1 shows the smallest version: each prediction depends on the token just selected, until an end marker or output limit stops the loop.

1.1 One decision at a time

Language models work with tokens: entries in a vocabulary, each identified by an integer. A token may represent a word, part of a word, punctuation or a special marker. The program that maps text to these integers is a tokenizer. The exact mapping depends on the model.

Our first experiment invents a vocabulary with five entries. Three stand for words; two mark the start and end. The integers and scores are chosen for this exercise.

The table plays the role of a very small prediction function. Unlike a Transformer, it uses only the last token and has no learned weights. This restriction makes every decision visible.

Choosing the largest score is called greedy selection. A language model usually returns scores called logits. A sampler can turn them into probabilities and draw a token, or use them to make a greedy choice. We will study sampling later. Here, max makes the choice deterministic.

The expression scores.index(max(scores)) finds the first position with the largest score. If two tokens tie, it therefore chooses the earlier one. The else attached to the for loop runs only when the loop reaches its limit without executing break.

The loop needs two ways to stop. The end marker lets the prediction function finish an answer. The output limit stops a function that never chooses that marker. Predict the result of generate(max_new_tokens=2), then try it in a Python session. Does the loop reach the end marker?

1.1.1 What depends on what

Let x1,…,xn denote the input tokens. A model with fixed weights 𝜃 supplies scores:

z = f𝜃(x1,…,xn).

The selection rule turns z into xn+1. The next call then uses the extended sequence. The symbol f𝜃 hides the neural network for now; the dependence between calls is what matters.

In ordinary generation, the next call needs the token chosen by the previous call. Knowing that an answer will contain ten tokens does not tell us which ten tokens to feed into ten independent calls. Later, speculative decoding will give us a way to propose several tokens and verify them. It must still respect the model’s generation rule.

1.2 Keep work that will be needed again

A simple implementation could pass the entire growing history to the model on every call. For a causal model, earlier positions cannot depend on tokens that have not yet been generated. Some work on those positions can therefore be saved.

To see the principle without introducing attention, use a prefix sum. Our second prediction function returns the sum of all input integers, modulo ten. The modulo operation keeps the output in the range zero to nine.

Starting with [1,2,3,5], the sum is eleven, so the next integer is one. Appending one makes the sum twelve; the next integer is two. Appending two makes the sum fourteen; the next integer is four.

There are two ways to do this. One sums the whole history each time. The other keeps a running total and adds only the newly generated integer before the next prediction.

Both versions produce [1,2,4]. The first performs fifteen additions: four before the first output, five before the second and six before the third. The second performs six: four to process the prompt, then one for each of the next two predictions.

For a prompt of length n and m ≥ 1 output integers, the first version performs

n + (n + 1) + ⋯ + (n + m − 1) = mn + m(m − 1) 2

additions. The second performs n + m − 1.

The final output has been emitted but has not been fed back into the prediction function. The history has seven entries; the running total covers six. If we wanted another output, we would first add the last emitted integer. Figure 1.2 separates the two boundaries. DeepInfer adds another: when a device result becomes available to the host. Its asynchronous scheduler must track these boundaries separately.

1.2.1 From a running total to a cache

The running total is a cache: saved information used to avoid repeating work. It is useful because it contains enough information for our next update. Appending a token preserves that property. Editing an earlier token without repairing the total would break it.

Transformer attention needs a richer cache. Earlier positions provide arrays called keys and values, which later positions use to compute their representations. Saving these arrays gives a key–value cache, usually shortened to KV cache. We will derive the arrays and their memory cost in later chapters. The running sum occupies constant space. A full-attention KV cache grows with the number of processed tokens, and each decode step still reads keys and values across that context. Caching avoids rebuilding them; it does not make attention a constant-cost operation. A sliding window bounds the context read by that attention layer, which changes both its memory use and what it can see.

Processing the supplied prompt is called prefill. Extending the sequence using saved state is called decode. In a conventional cached generation loop, the final prompt position supplies the scores for the first output token. The next model call processes that token to predict the second.

These names identify work, not a guarantee about how many device calls it takes. A long prompt may be split across several steps. A speculative step may verify several candidate tokens. Our simple loop gives us a starting point for understanding both changes.

1.3 Rebuild a lost window

How much history do we need to recover a cache? Change the predictor to the sum of the last three processed integers, modulo ten. A bounded deque holds that window: appending a fourth integer discards the oldest. This gives us the behaviour of a three-slot ring buffer without writing its index arithmetic.

The four outputs are [0,8,3,1]. At the checkpoint, seven entries have been processed, and the window is [0,8,3]. The latest output, 1, has been emitted but not processed. Taking the last three entries of the entire history would include it too soon. To continue after recovery, first process that 1: the window becomes [8,3,1], whose sum predicts 2.

Recovery is exact here because the state contains raw integers. The last three processed entries determine the whole window, regardless of the earlier history. DeepInfer’s sliding-window attention (SWA) bounded replay tackles a related problem, but reconstructs an approximate attention cache: hidden states inside the replayed suffix can depend on earlier context. Chapter 9 will explain that approximation alongside cross-layer sharing. Assessing it requires model-quality checks as well as checks of buffer contents [2].

1.4 Give an empty slot to another request

So far, one request has owned the loop. Now suppose three requests are waiting. For this experiment, A needs two output tokens, B needs four and C needs one. The engine can advance at most two requests in a round.

We make strong assumptions to isolate one scheduling decision. All requests arrive at the start. Each active request gains exactly one token per round. Every round costs one abstract time unit, however many slots are occupied. There is no prefill cost or memory limit.

A fixed-batch policy admits A and B together, waits until both finish, then admits C. A second policy refills an empty slot at the start of each round. Predict when C will finish under each policy.

BASH
python3 labs/03_batch.py

A finishes after round two under both policies. With fixed batches, its slot stays empty while B runs in rounds three and four. C must wait until round five. Refilling the empty slot lets C run in round three alongside B. Figure 1.3 compares the two schedules.

Both policies do seven units of useful token work. Fixed batches provide ten slot-rounds across five rounds and leave three unused. Refilling provides eight across four rounds and leaves one unused. B still finishes after round four; the shorter request benefits from the earlier admission.

Allowing batch membership to change between generation steps is often called continuous batching. Admitting C in an engine also requires prompt processing and enough memory for its state.

Notice that the scheduling policy never reads the remaining length when choosing the next request. The simulator uses that length only to decide when the simulated request finishes. A real engine generally discovers completion as generation proceeds.

1.5 What an engine must remember

The programs have acquired several kinds of state: token history and an output limit, reusable computation with a processed boundary, and a waiting queue with active slots and completion records.

For each request, an engine needs to answer at least four questions:

  1. Which input and output tokens belong to it?
  2. How much of that sequence has the model processed?
  3. Which memory holds the state needed to continue?
  4. Is it waiting, running or finished?

The engine also needs shared decisions: which requests to advance and how much work to admit. A scheduler makes those choices. A worker carries out the selected model work. The separation lets us discuss a scheduling policy without rewriting the prediction function.

There is a further complication when computation runs on another device. Submitting work may return before that work finishes. A request that has left a scheduling queue may still have a device operation using its memory. Resource lifetime therefore depends on completion, as well as logical request status. We will examine this in the chapter on overlapping host and device work.

1.6 Follow state through DeepInfer

DeepInfer’s README says it was originally built primarily on vLLM; this book has not identified the fork point. Its asynchronous execution makes the loop more demanding. Its zero-overhead batch scheduler (ZOS) overlaps host scheduling with device computation. The deployment Q&A credits SGLang and NanoFlow for earlier implementations of this approach [1, 2].

Follow one request through the ordinary offline interface: valid text token IDs, with no multimodal processor or structured-output grammar. We will read its admission, execution and result path, then revisit what happens when execution overlaps. This is a walkthrough of the inspected code, not a recorded engine run. Figure 1.4 gives the route. The arrows cross responsibility boundaries: the entry point prepares requests, the engine coordinates them, the scheduler selects work and the worker executes it.

The scheduler records an admission timestamp and appends the sequence to waiting. The C++ shared_ptr is an ownership handle; std::move transfers that handle into the queue without copying the sequence’s token history. The arrow in seq->request accesses a member through that handle. For a normal offline engine, the method also reserves capacity in vectors for output tokens and block references. Reserving a vector’s capacity is not allocating the device’s KV cache. That resource decision belongs to later scheduling and cache management.

This boundary explains why generate can submit many requests before running any model work. Admission records available work; scheduling decides what fits now. A useful consequence of this separation is that a new admission policy need not alter the model’s prediction function. We infer that benefit from the division of responsibilities, rather than from a stated design motive.

_post_process_step returns an empty address array when its argument is None. Otherwise it waits for sampling completion, prepares the model results and calls the engine’s post-processing callback. The engine updates sequence state through scheduler.process_outputs, then builds pooled request outputs. The outer loop can thus collect the same form of result from an ordinary step or the final drain. Clearing prev_step_state prevents that retained package from being consumed twice [5, 7].

1.6.6 An output has an owner and a lifetime

The comment immediately before RequestOutput.clone(raw_output) belongs to the call site above. It explains why the outer loop copies each output. The stronger ownership contract appears in LLMEngine.step:

Notice the return type: np.ndarray[np.uint64]. Its entries are integer addresses of C++ RequestOutput objects, not Python references to those objects. Keeping the array, or putting its integers in a Python list, preserves the addresses but does not keep the pointed-to objects alive. The C++ pool can destroy and reuse them at the next step [9].

The loop therefore calls RequestOutput.clone(raw_output) while each address is still valid. This static method is declared in deepinfer/_C/engine.pyi, line 182. Its C++ binding copies the object at the supplied address into a new object owned by the Python wrapper [10]. The docstring’s reference to pool.clone does not match that exposed API: use the entry-point call and the binding to identify the operation. A Python reference protects the copied object; an integer address does not protect the pooled original.

Cloning during collection preserves the result across the next pool release. Chapter 4 returns to the binding and pool implementation in Section 4.3.9, alongside the ownership rules for cached state. Here the caller needs one rule: copy a result while its address is valid.

1.6.7 Trace the same request across the boundaries

Our ordinary request now has a complete route. After admission it is a Sequence in waiting. When selected, its per-step metadata travels through the engine to the worker. Under ZOS decode, the worker retains the current step’s package and reports completed earlier work. Post-processing updates the request and creates output addresses; the offline collector copies them before the pool may reuse their storage.

For a concrete branch trace, suppose this request remains active after its last prompt chunk and through two ZOS decode calls. Name the decode packages D1 and D2. With no pending state on entry to that prompt call, the printed worker code gives:

The D1 call can return no output despite doing model work. The D2 call can return D1’s results while retaining its own. A later flush consumes whichever package remains. This predicts branch behaviour, not particular token values or the number of calls until the request finishes.

Three different objects therefore answer three different questions:

To investigate a missing final result, first compare the worker’s pending state with the outer loop’s flush path. To investigate results that change after a later step, inspect collection and cloning before changing sampling. These are different failure hypotheses because the execution and ownership boundaries are different. Chapters 4–6 will open the cache, scheduling and overlap boxes in the same map.

1.7 Experiments to try next

Keep the original scripts and saved outputs as a reference. Make each change in a scratch copy, and update its assertions when you deliberately change the expected result.

  1. Change a score so that the first program repeats steps. Does it reach the end marker, or stop at the output limit?
  2. Change the prefix-sum prompt and generate five integers. Check that both versions agree. Predict their addition counts before running them.
  3. In the window experiment, use width four and a two-integer prompt. Rebuild after the first output and again after several outputs. Does each recovered window predict the same next integer after processing the latest output?
  4. Give A and B the same length in the batching experiment. Does refilling still reduce the number of rounds?
  5. Give C a later arrival time. Which part of the simulator must change? Is an empty slot always evidence of a bad scheduling decision?
  6. Follow the printed worker branch with ZOS disabled, then enabled for decode. Which step’s outputs can the caller receive? Explain what final flush consumes in each case.
  7. Suppose the entry point keeps raw output addresses instead of cloning. Locate the operation that invalidates that choice. Why does keeping the addresses in a Python list not fix it?
