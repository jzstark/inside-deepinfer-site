CHAPTER 11

From an engine to a service

Chapter 10 examined correctness contracts within an engine. A service also passes requests and state between engines and storage. Those boundaries decide where work can run and what it must wait for.

The question

Four requests share a long prefix. Two prefill workers are available, but only one holds the prefix. Should all four requests wait for that worker? If both workers could reuse it, which queue would become shorter?

Run the service experiment:

BASH
python3 labs/23_service.py

All four requests arrive at time zero. Each prompt has 1,024 tokens, of which 768 can be reused. Matching takes one time unit; prefill processes 128 new tokens per unit. Two decode workers each need four units per request. A handoff adds one unit, with no limit on concurrent transfers. These are assigned costs. The workers serve one request at a time, without batching or eviction. Prefix fetching adds no delay in either case; only the P/D handoff has an assigned transfer cost.

The first case sends every request to the worker holding the local prefix. The second lets either worker fetch that same prefix, at the same assigned cost:

OUTPUT
Assigned time units; four requests, two P and two D workers
local affinity: P ends [3, 5, 7, 9]; D ends [8, 10, 12, 14]
shared cache: P ends [3, 3, 5, 5]; D ends [8, 8, 12, 12]

Saved output · results/23_service.txt

With local affinity, prefill finishes at 3, 5, 7 and 9. With a shared cache it finishes at 3, 3, 5 and 5. The last answer arrives two units earlier, not four: decode now makes the last pair wait. With equal handoff delays, sharing saves two units in both comparisons: 14 versus 12 with a one-unit handoff, and 16 versus 14 with a three-unit handoff. A shared cache with the slower handoff finishes no earlier than local affinity with the faster one. That comparison changes two variables: the extra transfer cost offsets the saving from sharing.

The no-hit case supplies a baseline for reuse: both prefill workers remain available, but processing all 1,024 positions per request moves the last completion from 12 to 22, with the handoff delay held at one unit.

Scope and order. We follow the deployment Q&A from prefix matching to routing, state movement and token output. Released DeepInfer code fixes the engine roles and the state layout at those boundaries. The Q&A describes the service that connects them. We then audit a published performance curve, using chapter 2’s accounting and chapter 8’s acceptance model. Our experiments calculate queues and rates; they do not run a serving cluster.

11.1 A request crosses several owners

The engine of chapter 1 was responsible for advancing requests. A service must first decide which engine should own each request and how its reusable state will reach that engine. Figure 11.1 separates the request’s route from the storage it can use. A released component does not imply that its production orchestration is also released.

These are executable role boundaries. They do not locate the machine-selection policy, the network transfer, or the service’s retry logic. The distinction also matters when reading benchmarks: examples/benchmark.py constructs its LLM through create_llm without overriding the engine role. It therefore uses EngineArgs.engine_type = EngineType.NORMAL, the default at deepinfer/engine/arg_utils.py:41. The examples README calls the separate prefill and decode measurements “Stage decoupling”. Those windows are inside one combined engine deployment; they are not a disaggregated P/D service [17, 15, 83].

The Q&A identifies one property shared with the DeepSeek-V3/R1 inference system: attention uses data parallelism, with equal DP and EP sizes. It also points to DualPath’s intra-group scheduling for the decode balancer, but gives no link or bibliographic reference for DualPath. These establish a stated continuity in that parallelism choice and an acknowledged scheduling precedent. The separate 3FS repository is a dependency boundary. None establishes a line-by-line derivation of the service code, which is absent here [2, 86].

Image requests add an encoder before prefill: the Q&A describes E/P/D separation. Its vision-encoder balancer first chooses a machine randomly, then chooses the GPU with the fewest assigned patches, counting width and height in patch units. Recipe handles the API-to-model representation. This adds a workload and a queue to the map, without changing why prefill and decode need different capacity signals [2].

11.2 Hits decide prefill demand

A prefix hit is useful before any bytes move. The Entrypoint matches a hash chain against metadata in the local kvcache-store’s CHECK role. A hash chain identifies a block together with its preceding prefix, so reuse concerns a matching history, not just an equal block of tokens. The resulting hit length determines how much prompt work remains. Routing needs that answer; the Q&A explicitly says matching cannot be hidden [2].

For prompt length L and computation resuming at H, let q = L − H. Chapter 5’s documented quota model estimates work from the new positions q and their existing context c. The service can then choose a prefill tier, an engine with quota left, and a rank within it:

match→H→(q,c)→cost ⁡ (q,c)→routing and capacity.

The quota fit and its service driver are described in the Q&A, not implemented in the released scheduler. A cache hit also leaves context to read; reducing new positions does not remove all attention work.

The storage placement changes a routing constraint. With block KV in a separate shared cluster, every prefill engine can hit any prefix. It need not wait for the compute machine that produced that prefix. This is the Q&A’s reason for having no prefix-affinity routing.

Our lab holds the prefix and fetch costs fixed and changes only the eligible workers:

A local-cache service could instead route to an idle worker and recompute the prefix. That is another policy, not tested by the affinity case. Real shared storage pays for fetching and can itself queue. The experiment isolates the benefit of removing ownership affinity; it does not predict that shared storage always wins.

11.2.1 From work to a capacity estimate

Let λ be requests per second, L their fixed input length, O their fixed output length, and h the fraction of input tokens reused. Suppose vP and vD are sustained per-GPU rates for this workload. At a target utilisation u, a simple capacity estimate is

GP = ⌈λL(1 − h) uvP ⌉ ,GD = ⌈ λO uvD ⌉ .

This linear teaching model suppresses context-dependent cost, batch shape and EP group granularity. Its units are GPU equivalents, not deployable group sizes. Lab 23 assigns λ = 4, L = 1024, O = 64, vP = 2048, vD = 128 and u = 0.8:

OUTPUT
Capacity model (GPU equivalents, not deployment sizes):
reused input fraction 0%: P=3, D=3
reused input fraction 75%: P=1, D=3
Saved output · results/23_service.txt

The arithmetic moves prefill from three GPU equivalents to one. Output work stays at 256 tokens/s, so the decode estimate stays at three. That conclusion holds the arrival rate, output lengths and decode rate fixed. Faster prefill can still change when requests reach decode, as the opening experiment showed. It can also change achievable batching and latency. Production sizing cannot replace those effects with a constant vD without checking the workload.

The meaning of h matters. One hundred requests might all hit ten tokens of a thousand-token prompt: the request hit rate is 100%, but only 1% of input tokens are reused. The Q&A sizes prefill from non-cached tokens and decode from running requests. It reports that shortening chatbot retention from seven days to about three costs 0.5–1% of KV-cache hit rate. It does not specify here whether that is a relative loss or a loss in percentage points, or give the corresponding uncached-token demand. Neither should be silently substituted into our formula [2].

Matching is on the routing path; fetching has a different dependency. The Q&A describes a separate process fetching block KV from 3FS into host shared memory, followed by an engine thread swapping it into device memory. Per-layer host-to-device copies can overlap forward computation once the needed state is ready. It describes using an RDMA network interface for these transfers through PCIe, avoiding GPU compute cores. This is a documented transfer design, not a path implemented by our queue simulator [2].

11.3 State lives in three places

Chapter 4 separated block KV from per-request state. At service scale these objects also have different homes and failure modes (Table 11.2).

The Entrypoint maintains an in-memory directory for the single host copy of SWA. A cross-machine hit pulls that state over the network. Host restart or eviction can therefore remove SWA while the block KV still exists. This is a normal trigger for chapter 9’s encoder replay, distinct from decoder replay on every truncated prefill. The Q&A also says decode KV is written to storage for later reuse, but active decode does not use KV offloading [2].

11.3.2 Retention is not one number

A retention target, a capacity calculation and an eviction rule answer different questions. The Q&A gives all three, listed in Table 11.3. There TTL means time-to-live and LRU means least recently used.

The Q&A places expiry and reclamation in 3FS’s GC, with no expiry logic in kvcache-store itself. It does not give the complete precedence rules between age and occupancy pressure. A server sized for a day’s data does not by itself promise that every object will survive for that day, or that the whole cluster retains only a day [2].

Durability and read latency are separate again. The Q&A specifies 10+2 erasure coding, tolerating two simultaneous node failures, and says a read contacts 11 storage nodes and returns after any ten replies. Coding redundancy and read fan-out are different counts. The description does not explain why that read uses eleven nodes for twelve coded fragments; we do not infer a placement rule from those numbers. Nor does storage redundancy replicate the single host copy of SWA [2].

For L = 902, the cap is exactly 768. With SWA present, prefill starts at 768 and processes 134 new positions. Without it, prefill starts at 640. The interval [640,768) reconstructs encoder SWA; its block KV is already available and need not be rewritten. The remaining 134 positions are new. Calling both lengths simply “the hit” hides this distinction between reused bytes and avoided computation [2].

The checks enumerate aligned candidates independently and compare the result with the formula. They also verify nonnegative lengths, the cap, alignment, and a one-block backoff only when there is a positive hit and SWA is absent. Prompts shorter than 134 + 128 = 262 cannot have a positive block hit under this policy. Monotonicity holds in the lab with cache extent and SWA availability fixed. It need not hold across changing directory entries in a live service.

The same L = 902 case exposes chapter 9’s integration gap. A 140-row retained suffix starts at 762, six positions before a hit at 768. Without an additional validity restriction, the released visibility formula can read those six consumer ring entries, but the stored-state restore does not fill them. Backing off after an SWA miss gives more rows; it does not resolve the SWA-present case. The numbers 128 (window), 134 (default ring and documented hit reserve) and 140 (suggested keep count) retain different meanings. The released helper’s truncation guard narrows the allowed configurations, but does not disclose how the production driver reconciles the six entries. This experiment tests the Q&A’s policy arithmetic, not that missing integration [84, 2].

11.5 Balancing, scaling and failure

The Q&A describes four load-balancing concerns: prefill, decode, vision encoding and expert parallelism. Chapter 7 already traced the released EPLB statistics, policy and weight movement. At the service boundary, the remaining question is which engines should receive work and how many should exist.

Prefill is divided by total context length into four tiers: below 16K, 16–64K, 64–256K and at least 256K. Each tier has a compute-quota cap. Engines pull requests according to remaining quota; within a DP group, new requests go to the rank with the least current quota load. The previous round’s share of quota demand controls how many engines each tier receives. These policies use the hit-derived work estimate, rather than sending every request with a given prefix to its old owner [2].

Decode has two load measures. A rank with few running requests might already hold a large total KV length. The documented policy sends short requests towards low concurrency even if that rank has much KV, and long requests towards small total KV length. This is where the Q&A acknowledges DualPath’s intra-group scheduling. Counting requests alone would miss the context-reading cost from chapters 2 and 3 [2].

Autoscaling follows the same division: prefill demand is non-cached tokens; decode demand is running requests. The Q&A adds rate limits, minimum and maximum sizes, spare quota and a rule forbidding scale-in above 0.8 quota utilisation. The capacity formula in lab 23 explains the direction of change, not those production thresholds or their control loop.

Scale-in and failure also have different contracts. On a planned shutdown a CE gets a one-minute grace period, then forwards unfinished requests and their KV in one transfer to other CEs. A crashed engine cannot promise to perform that handoff. The Q&A instead describes quota redundancy and request rerouting; restarts take minutes. A failed GPU invalidates the whole instance’s EP communication domain. On restart, the platform forms an EP size from the healthy GPUs it can allocate. This describes recovery of service capacity, not evidence of uninterrupted, exactly identical output for an affected request [2].

11.6 Check a published curve

Once stages have separate capacities, we need to choose their operating points. A decode configuration may serve each user more slowly while producing more tokens per GPU overall. The useful comparison is a Pareto frontier: the points for which no other tested point is at least as good on both axes and strictly better on one.

The fixed release has three performance figures under doc/images/: decode_pareto.png, prefill_pareto.png and wide_ep_decode_pareto.png. It supplies a sweep script and plotting code, but no raw results.jsonl. The sweep creates that file when run. We can inspect the conversion and read an approximate point from the image; we cannot reanalyse absent raw measurements [85].

For the published decode figure, EP and DP are both 64, context length is 131,072, and nextn=3 is fixed. Its subtitle supplies 75% acceptance and τ = 3.25. There are two plausible meanings of a. If it means the mean number of accepted draft tokens divided by three, then τ = 1 + 3a is precisely the intended conversion, ignoring end-of-request clipping. But if it means a conditional acceptance probability of 0.75 at each successive draft position, chapter 8’s accepted-prefix rule gives

E[accepted drafts] = a + a2 + a3 = 0.75 + 0.5625 + 0.421875 = 1.734375,τ = 2.734375.

The second and third positions count only when all preceding draft tokens were accepted. Equal conditional probabilities suffice for this product; the lab uses independent Bernoulli draws as a simple exact enumeration of that case. One main-model token is included per step, with no early EOS in this model.

11.6.3 Recover a step rate; specify the missing measurement

The published 64-request point is approximately 246 tokens/s/user, read from the image rather than a raw record. Under the figure’s τ = 3.25,

SPS ≃ 246 3.25 = 75.69,y ≃ 75.69 × 64 × 3.25 = 15,744tokens/s/GPU,

using CP=1. That agrees with the plotted point near 15,750. It is not the throughput of the entire 64-GPU instance. The image hash and fixed revision are recorded separately in the source manifest; the reading remains approximate.

Neither decode axis is a latency percentile. The reciprocal of user speed is an amortised time per output token; speculative steps can publish several tokens together. It does not reveal the gaps between bursts, queueing, or time to first token. The prefill figure uses mean measured step duration on its horizontal axis, which also omits a request’s earlier waits. Chapter 2’s request trace is the appropriate model for those quantities.

A measurement capable of changing the conclusion would record useful emitted tokens per request-step under the same model, prompt histories, sampling parameters and fixed draft length. It should count early termination and rejected drafts, then estimate τ at each concurrency instead of supplying one acceptance number. Keep raw records and token timestamps so that steady-state rates and end-to-end gaps remain distinguishable. First this checks the figure’s absolute scale; varying τ by point also tests its ordering.

The Wide-EP comparison needs a second control: repeat EP8 and EP64 on matched hardware and workload definitions, recording topology, model and dependency revisions, expert redundancy and the actual acceptance factor. Compare their frontiers at the same per-user target and per-GPU denominator, not merely at the same total request count. A different mapping from step rate to useful output could change the observed advantage. So could service queueing absent from the offline benchmark. This is a proposed measurement, not a result of our synthetic records.

11.8 One request, end to end

Follow request A with a 300-token prompt through the released offline path. Use a NORMAL engine, CP=1, ZOS enabled and fixed verification with nextn=5. Leave chunked prefill, YOCO truncation and structured output off. Assume enough free memory, no prefix hit or preemption, and an output limit that does not interrupt the steps below. Experts occupy the configured EP group; other requests keep decode calls running after A finishes. The lengths and acceptance outcome below are assigned to illustrate the inspected branches, not recorded engine output.

11.8.1 Admit the prompt and create the first output

LLM.generate admits A as a persistent Sequence in the waiting queue. When the scheduler selects its prompt, A receives three paged blocks, ⌈300∕128⌉ = 3, and a state slot. The block table locates compressed KV and index rows; the slot holds SWA and live compression state. No other request owns these allocations in this case (chapters 1, 4 and 5).

The worker sends the 300 prompt positions through embeddings and the model layers. Attention writes and reads the layer’s cache views; MoE sends each position’s expert work to the selected slots and returns the weighted results (chapters 3 and 7). Sampling uses the last prompt position’s representation to choose A’s first output. Prompt post-processing happens in the same worker call. The processed count is now 300, while token history has length 301. The output at position 300 still needs to become a model input.

11.8.2 Follow one six-position decode step

After further decode work, choose a step N whose inputs begin at position 320 and include five available drafts. During call N, the host processes N − 1: A’s committed count becomes 320 and its history length 321. Forward N is already queued. Its six queries occupy positions 320–325, with key length 326. For example, position 320 lies in A’s third logical block at token-position offset 64; the block table supplies the physical block ID.

Assume verification accepts the first two drafts and rejects the third. The accepted prefix and its replacement contribute three output tokens. The six evaluated positions therefore advance the committed count by three, not six. The last output remains unprocessed:

Before that last update, scheduling N + 1 sees 320 committed positions, six in flight and six new queries: an upper-bound key length of 332. On the device, the previous accepted count removes 5 − 2 = 3, giving 329. The new queries actually cover positions 323–328. Their main input and drafts come from step N’s device output via the request remap, even though the host does not yet know them (chapters 6 and 8). The three blocks still suffice. Discarded draft bytes may remain in storage; counts and visibility decide which rows can be read (chapter 4).

Only after queuing forward N + 1 does the worker wait for sample_end_evt(N) and post-process those three outputs. The entrypoint clones the returned pooled records while their addresses remain valid. Counting the six queries as six useful outputs would double this step’s progress; timing submission alone would miss the wait and publication boundary (chapters 1 and 2).

11.8.3 Finish, then change the boundary

Suppose a later step M produces EOS. Call M + 1 has already queued A’s extra forward before post-processing marks it finished. In call M + 2, scheduling removes A; post-processing waits for the obsolete M + 1 work and skips its output; pre_sampler_sync then releases A’s remaining storage. Other requests keep these decode calls consecutive, as assumed in chapter 6’s trace. At the eventual end of the whole generation loop, the final flush drains the remaining in-flight result. Request completion, output collection and storage release are distinct events.

Two changes connect this trace to the remaining chapters. Enabling compact prefill would introduce chapter 9’s full-source and retained-query layouts; agreement with mask would still not prove agreement with this untruncated baseline. Moving A to a disaggregated service would introduce prefix matching, PE selection and a PE-to-CE state handoff. The CE needs the live state extent, including the dropped region; the released layout helper does not implement that transport. These are changes to the case, not hidden steps in its offline execution.

Finally, choose the comparator before testing either change. Chapter 10’s golden trajectory can hold A’s tokens fixed for a numerical comparison; independently sampled outputs answer a different question. This single request now gives us both a route through the code and a way to investigate it: name the owner, locate the processed boundary, identify the completion condition, and state which observable a proposed change must preserve.
